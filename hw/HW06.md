## Part 1: Shannon encoding

Work in `Shannon.py` and `encode_decode.py`. You will construct a codebook
from one source text and use that same codebook to encode and decode other
messages.

### Background: why use different numbers of bits?

An **encoding** assigns a bit string, called a **codeword**, to each
character. Encoding a message means replacing its characters with their
codewords; decoding reverses that process. This is lossless compression:
the goal is to recover the original message exactly, not to hide its contents.

A fixed-length code for four characters could use `00`, `01`, `10`, and
`11`, spending two bits on every character. If some characters occur much
more often than others, we can instead give frequent characters shorter
codewords and rare characters longer ones. What matters is the **average**
number of bits, weighted by how often each character appears.

The information content of a character with probability `p` is `-log2(p)`
bits. A character occurring half the time has information content 1 bit;
one occurring one eighth of the time has information content 3 bits.
Entropy is the average information content across the character distribution:

```text
H(C) = sum over characters c of p(c) * (-log2(p(c)))
```

Shannon encoding turns these possibly fractional information values into
whole-number codeword lengths, then assigns bit strings of those lengths.
The construction below is all you need for this assignment; no prior
coverage of Shannon encoding is assumed.

### Prefix-free codes: decoding without separators

Different-length codewords must have recognizable boundaries. Consider
`A → 0` and `B → 01`. Here the codeword for `A` is the beginning of the
codeword for `B`, so reading a `0` does not immediately tell you whether to
output `A` or wait for another bit.

A **prefix-free code** avoids this problem: no complete codeword is the
beginning of another codeword. For example:

```text
C → 0      A → 10      B → 110      D → 111
```

Reading from left to right, you can emit a character as soon as a complete
codeword is recognized, then start again. No separator bits are necessary.
The boundaries in `10 | 110 | 0 | 111` reveal the message `ABCD`; the actual
encoded string is just `101100111`.

### Construct a Shannon codebook

Use the **cumulative-probability construction** below. Start with a nonempty
character-probability dictionary whose values are positive and sum to one.
For now, assume it contains at least two distinct characters.

1. Sort the characters from most probable to least probable. For equal
   probabilities, preserve their order in the input dictionary. When building
   that dictionary from text, insert characters in first-occurrence order.
2. For each character, calculate `L = ceil(-log2(p))`. The ceiling rounds
   **up** to the nearest integer. For instance, `p = 0.3` gives
   `-log2(p) ≈ 1.737`, so `L = 2`.
3. Calculate `q`, the sum of the probabilities of all characters **before**
   the current character in the sorted order. The first character has
   `q = 0`. Do not include the current character's probability yet.
4. Write `q` as a binary fraction and take its first `L` digits after the
   binary point. Those digits are the codeword. Keep leading zeros and
   append trailing zeros if the binary expansion terminates early.
5. Store the character/codeword pair, add the current probability to the
   cumulative sum, and continue to the next character.

Sorting, using the cumulative probability *before* the current character,
and retaining the prescribed number of digits are all necessary parts of
this construction. The result is prefix-free. This is Shannon's cumulative
construction, not the recursive splitting algorithm sometimes called
Shannon–Fano coding. See the source-coding discussion in
[Shannon's original paper](https://essrl.wustl.edu/~jao/itrg/shannon.pdf)
for additional background; reading the paper is optional.

### How to obtain digits of a binary fraction

Binary places after the point have values `1/2`, `1/4`, `1/8`, and so on.
For example, `0.101` in binary means `1/2 + 0/4 + 1/8 = 0.625`.

You can generate the first `L` digits of `q` without a special conversion
library. Start with a remainder equal to `q`. Repeat the following `L` times:

- double the remainder;
- record its integer part, which will be `0` or `1`; and
- subtract that integer part to obtain the next remainder.

For `q = 0.625` and `L = 3`:

| Step | Double the remainder | Record | New remainder |
| --- | --- | --- | --- |
| 1 | `2 × 0.625 = 1.25` | `1` | `0.25` |
| 2 | `2 × 0.25 = 0.5` | `0` | `0.5` |
| 3 | `2 × 0.5 = 1.0` | `1` | `0.0` |

The resulting digits are `101`. If the remainder becomes zero before you
have `L` digits, the remaining digits are zeros.

An equivalent approach is to compute the integer `floor(q * 2**L)` and
write it in binary using **exactly `L` digits**, padding on the left with
zeros. Truncate rather than round. For example, `q = 0.4` and `L = 2`
gives `floor(1.6) = 1`, whose two-digit representation is `01`, not `1`.
Python's `bin()` accepts an integer, not a fractional probability, and its
`0b` prefix is not part of a codeword.

### Worked example: from probabilities to codewords

Suppose the input probabilities are `A: 1/4`, `B: 1/8`, `C: 1/2`, and
`D: 1/8`. Sorting gives `C, A, B, D`; the tied characters `B` and `D` keep
their input order.

| Character | Probability `p` | Earlier probability `q` | Length `L` | Codeword |
| --- | --- | --- | --- | --- |
| C | `1/2` | `0` | `1` | `0` |
| A | `1/4` | `1/2` | `2` | `10` |
| B | `1/8` | `3/4` | `3` | `110` |
| D | `1/8` | `7/8` | `3` | `111` |

For `B`, the cumulative probability is `1/2 + 1/4 = 3/4`, whose binary
expansion is `0.11000…`. Keeping three digits produces `110`. This is
why the cumulative sum, rather than the character's own probability,
determines its particular bit string.

The expected codeword length is:

```text
(1/2 × 1) + (1/4 × 2) + (1/8 × 3) + (1/8 × 3) = 1.75 bits/character
```

For this distribution, that is shorter than the two-bit fixed-length code.
This comparison counts the message bits and assumes the codebook is already
shared; storing or transmitting the codebook would add overhead.
It also equals the entropy because all the information contents are already
integers. For other distributions, rounding the lengths up can add some
cost; Shannon's expected length is at least the entropy and less than one
bit above it.

This is an expectation under the source distribution, not a promise that
every particular message gets shorter. A message containing only `D`s would
use three bits per character with this codebook.

### Decode one codeword at a time

For encoding, look up each input character's codeword and concatenate the
results. For decoding, a reverse dictionary maps complete codewords back to
characters. Keep a buffer that is initially empty:

1. Add the next input bit to the buffer.
2. If the buffer matches a complete codeword, emit the corresponding
   character and clear the buffer.
3. Otherwise, keep reading bits until a complete codeword is recognized.

With the example codebook, reading `1` is not enough to emit anything;
reading `10` completes `A`. The prefix-free property guarantees that you
will not need to undo a completed match. A decoding tree is another valid
implementation: follow a branch for each bit, emit a character at a leaf,
and return to the root.

The recovered text must match exactly, including spaces, punctuation, and
line breaks. Treat an unrecognized character, a nonbinary input digit, an
impossible prefix, or an incomplete codeword left at the end as an error;
do not silently discard it. Encoding or decoding an empty message should
return an empty string.

For a source alphabet containing just one character, the length formula
would produce zero bits and lose the number of repetitions. Use the
one-bit codeword `0` for that special case. An empty source cannot supply a
probability distribution. The tweet source has many distinct characters,
so neither special case affects its expected-length comparison.

### Calculate entropy

Begin with a method for the entropy of the class label `Y`:

```text
H(Y) = -sum over classes k of P(Y = k) * log2(P(Y = k))
```

Estimate class probabilities from their frequencies in the partition. A
class with probability zero contributes zero to entropy; skip that term
rather than evaluating `log2(0)`. Do not apply HW05's Laplace smoothing here:
these calculations use the observed class proportions.

Useful checks are:

- a partition containing only one class has entropy `0`;
- two equally common classes have entropy `1` bit; and
- a binary class distribution has entropy between `0` and `1` bit.

### Calculate conditional entropy and information gain

For a categorical feature `X`, split the partition by feature value. Compute
the label entropy within each nonempty group, then weight each group's
entropy by its fraction of all examples:

```text
H(Y | X) = sum over values v of P(X = v) * H(Y | X = v)
IG(Y, X) = H(Y) - H(Y | X)
```

Use each group's own size when computing its class proportions. Use the
full partition's size when computing its weight. Do not take an unweighted
average of group entropies unless all group sizes are equal. A possible
feature value with no examples contributes zero to the weighted sum.
